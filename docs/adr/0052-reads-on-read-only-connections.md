# The interface's reads on read-only connections beside the writer

`store.Open` opened one SQLite connection, and the interface, the sync workers, the scanner, the labeler, rules and `godwit mcp` all shared it. mygo's `sqlite.DB` runs one operation at a time behind a one-slot gate, so every call waited for every call queued before it. On a 2.8 GB mailbox during a sync the connection was busy 53 of 61 s: a sub-millisecond `ListAccounts` waited up to 23 s, a new message 2 to 3 s, and opening a message while scrolling waited behind the sync's batches, the window's saved-view recounts, the avatars' sender scans and the previous message's `ThreadDeadline`. The database already runs in WAL mode, where readers on other connections run beside the writer.

## Decision

- **`store.DB` keeps one writer and adds two read-only connections for the interface** (`sqlite.OpenOptions{ReadOnly: true}`, 5 s busy timeout, `PRAGMA cache_size = -1024`), opened on the first read that goes to them, after `Open` has migrated. Callers do not change: routing happens inside `store.DB.Query`.
- **Only the interface's plain SELECTs go to a reader.** A context marked with `store.WithUIRead` (the core marks every `ui`-role connection in `core.WithUISession`, so every Service method the window and the tray call carries it) sends a statement to a reader when its first keyword, after blanks and comments, is `SELECT` and it calls none of `last_insert_rowid()`, `changes()` and `total_changes()`, which read the writer's connection state. Everything else stays on the writer: PRAGMAs, `WITH` (a write can follow it), `INSERT … RETURNING`, anything not recognized, `Execute`, `Transaction`, `DurableTransaction`, `DurableExecute`, and every read without the mark (sync, rules, labeler, scanner, `full` and `mcp` clients). The read-only open is the safety net: a write that reaches a reader fails with `SQLITE_READONLY`.
- **The mark ends with the interface's connection.** It holds the connection context's `Done` channel, so work that an interface call detaches with `context.WithoutCancel` (ImportAccounts' reads after its commit, the compose cleanup paths) reads on the readers while the window lives and on the writer once it has gone. `store.WithoutUIRead` takes the mark off: a Wit run started from the window (`runCaller`) is the backend's work and reads on the writer, as a `godwit mcp` agent's run does.
- **The backend's own work keeps its one connection** (all of it, except reads that interface calls detach while their window lives, above). An earlier version sent background reads to a shared reader too. The sync then ran 8 times faster and took the CPU from the interface: an opening during a sync got slower (14 s to 28 s). Kept on the writer, background work runs exactly as before, minus the interface's reads it used to queue behind.
- **Reads see every committed write.** mygo has no interactive transaction: `Transaction` is one batch under `BEGIN IMMEDIATE` inside one gate hold, and `Query` refuses `BEGIN`. So a write has committed when its call returns, and a read started after it, on any connection, sees it. A read that runs while another goroutine's transaction is open sees the state before that transaction, which the single connection also allowed, since nothing ordered the two calls.
- **Two lanes keep quick reads from queueing behind the interface's own scans.** Reader 0 is the quick lane, reader 1 the long lane. A long read takes the long lane only. A quick read takes the quick lane, else the long lane when it is free, else whichever frees first, so it waits at most for one statement. A read is long when its context is marked with `store.WithLongRead` or when its statement's last run took 250 ms or more. The core marks the scans it knows: a saved view's evaluation (its reply statuses included) and placement, the contacts (`Find`'s recipients, the contacts list) and the sender scans of `ContactAvatar`.
- **A scan the user waits on never queues behind the long lane.** A reader message's `ThreadDeadline` computes the reply statuses of the whole mailbox (until a per-thread read lands). Marked long, it queued on reader 1 behind the window's saved-view recounts and the avatars' scans: while scrolling during a sync a new one came every 300 ms, the queue grew faster than it drained, and the badge waited up to 9.6 s. `store.WithForegroundScan` (on `ThreadDeadline` and `deadlineWrites`) makes a read take the long lane when it is free, else the quick lane when it is free, else whichever frees first, and its run time never makes it long. So it can hold the quick lane for one statement (about 100 to 200 ms on the fixture), which a thread opened next then waits for at most. `WithLongRead` wins over it. The marks matter at a cold start: a new process has no run times, and in an earlier version, where a statement not run yet could take any lane, the boot's saved-view scans held every reader on a cold page cache and a 2 ms `ListAccounts` waited 4.2 s. The run-time table catches scans nobody marked after their first run; it is keyed by statement text and bounded (256 entries, cleared when full).
- **The readers must not keep the WAL from restarting.** The WAL starts over only after a checkpoint has copied all of it back, and a checkpoint stops at the oldest snapshot a reader holds. During a sync the writer commits every few milliseconds while the two readers run statements back to back, so some reader nearly always holds a snapshot older than the last commit, and the WAL grows with everything the sync writes: perfbench measured 1.2 GB after 27 s of the window part (23 MB on the single connection), and the file keeps its largest size. So when the WAL passes 64 MB, the backend's writes (`store.DB.Execute`, `Transaction`) wait while a drain empties the readers: interface reads take the writer, which the paused writes leave free (a read already waiting for a lane stops waiting and takes it too), the drain takes both lanes as soon as their running statements end, and `PRAGMA wal_checkpoint(TRUNCATE)` on the writer empties the file. The interface's own writes never wait. A drain gives up after 30 s, and the next one comes 5 s later; so does it when the checkpoint could not empty the WAL, because another process reads it. A long reader statement therefore pauses the sync once the WAL is full, as it paused it on the single connection, but never the interface.
- **The SQL trace names the connection.** `GODWIT_SQL_TRACE` lines keep their five fields; the kind is `q`, `x` or `t<n>` on the writer and `q@r<i>` on reader `i`. perfbench computes queue wait and run time per connection.

## Considered options

- **A priority gate on the one connection** (interface calls first). It reorders the queue, but a call still waits for the statement that holds the connection, and one saved-views or sync statement runs for seconds.
- **Background reads on a reader as well.** It frees the writer for the sync, but the faster sync competes with the interface for CPU (measured above), and the interface's reads then wait for that reader's scans too.
- **Three readers, the third shared with the backend.** About 7 MB of RSS per reader (measured); two cover the interface once the backend keeps the writer.
- **Lanes by run time only, no marks.** It needs no caller to change, but every statement is new in a fresh process, which is when the window and its scans start together.
- **Read-write connections with `PRAGMA query_only`.** A misrouted write would still be refused, but a read-write connection can also run checkpoints and create the WAL. Read-only is the narrower promise.
- **`PRAGMA mmap_size` on the readers.** Not measured; mapped pages count as file RSS.
- **Let any long read take the quick lane when the long lane has a queue and the quick lane is idle.** It also fixes the deadline badge, but a saved view's 0.8 s statement or the palette's 16 s contacts scan would then hold the quick lane that the next thread waits for. Only the reads the user waits on (`WithForegroundScan`) may take it.
- **`PRAGMA journal_size_limit` alone.** It shrinks the WAL file when the log restarts, but the log never restarts while the readers are busy.

## Consequences

- No new egress, no new `core.Service` method, no schema change.
- The interface's writes (`SetFlags`, `NewDraft`) still wait for the writer, behind the backend's work, as before.
- A long reader statement delays the end of a WAL checkpoint; past 64 MB of WAL it also pauses the backend's writes until it ends (or 30 s). Readers hold their snapshot only for one statement.
- A scan the core adds later should take `store.WithLongRead`; until it does, its first run in each process may hold the quick lane.
- Something that needs no other connection open (`journal_mode = DELETE` in the dev database copy, `core/devsync.go`) must not read through `store.DB.Query` with an interface context first, or must close the store; the readers open only on the first routed read for that reason.
- A temporary table or an attached database exists only on the connection that made it, so a reader would not see it. Godwit has none; adding one needs a way to read on the writer first.
